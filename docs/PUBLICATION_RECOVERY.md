# 发布诊断与恢复操作

## 只读检查

在项目根目录运行：

```bash
.venv/bin/python -B -m app.publication_audit
.venv/bin/python -B -m app.publication_audit --verify-snapshot
```

工具以 mode=ro 打开 SQLite，不初始化数据库，不写 share。不扫描完整历史，只核对最新数据库快照、当前主榜/派生榜、registry 声明的班级/专业文件及对应历史索引。第二条额外解压最新一个 gzip（解压数据上限 32 MiB）；默认只检查该文件存在，不能据此声称内容完整。输出不包含个人记录。

退出码 0：数据产物版本一致；1：缺失、损坏、版本不一致或无法读取；2：调查期间出现新提交，或近期采集状态仍为 publishing，暂按过渡状态处理。publishing 超过 15 分钟不再用它掩盖不一致。工具报告当前版本一致性，不保证数据新鲜，也不验证所有历史文件；须同时核对 fetched_at、认证状态和最近成功日志。图片异步生成，单独报告 current/pending/unavailable，不把图片滞后等同于数据库发布失败。

## 处理顺序

1. 若 in_progress，先等待正在进行的串行发布结束，再重查；不要并发启动回填、重导出或重启正在工作的采集服务。
2. 若 partial，检查 issues 所列产物和采集日志中的对应发布失败类别。分别确认磁盘剩余、文件权限、历史锁竞争、文件损坏；不要删除索引或旧产物来“消除”错误。
3. 修复实际原因后，下一次正常成功采集会发布新的当前榜及派生榜。不要把较新的成绩附到旧 snapshot_id，也不要从 Bot 反向写共享数据。
4. 最新历史文件缺失、gzip 孤立或历史索引损坏是单独的数据维护任务。现有回填可补合法孤立文件的索引，但不自动清空损坏索引或覆盖同 ID 冲突内容。执行前确认采集端已升级共享锁协议、数据库备份可恢复，并确定 I/O 预算、范围和并发写者。
5. 图片 pending 且资源保护开启时等待正常队列恢复；不提高限额、不重启采集、不触发全榜渲染来催促图片。缓存生成时间与最新核对时间按现有协议区分。

2026-09-25 已增加当前数据不可变版本目录与原子指针切换，并更新采集/渲染/Bot 消费协议，详见 DATA_PUBLICATION.md。SQLite、历史统计和图片仍为独立提交边界；诊断不会自动修复这些差异。每个部署都须通过真实成功采集验证版本切换。

## 渲染连接保护

默认 RENDER_MAX_CONNECTIONS=64（允许 1–256），RENDER_SOCKET_TIMEOUT=5（大于 0、最多 30 秒）。请求整行采用绝对读取截止时间，持续发送零碎字节不能延长占用。上限在创建线程前获取；超过上限关闭连接，插件沿用文字回退。任务等待保持 RENDER_REQUEST_TIMEOUT 默认 90 秒，限定为有限正数且不超过 300 秒。写响应也有超时。断连、超时和线程创建失败均释放配额。

该连接上限与任务队列上限分开；相同请求合并仍保留，预渲染上限仍为 3。renderer 运行状态增加 active_connections。不要在生产使用大量连接压测；并发、慢发送及释放测试使用临时 Unix socket。
