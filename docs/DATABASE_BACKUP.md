# SQLite 在线备份与隔离恢复

数据库是完整历史源；源码/unit 备份不能代替它。本工具只备份 SQLite，不包含浏览器认证、配置 Secrets、Bot 会话、share 或图片。数据库含学生数据，必须留在私有存储，不进入 Git、share 或公开报告。

## 备份流程

`python -B -m app.database_backup backup --source /绝对路径/rank.db --output /私有目录/新备份.db`

必须通过低优先级和明确的 cgroup I/O 预算运行。生产默认由外部一次性 systemd 作业限制 CPU 25%、内存 192 MiB、读 8,000,000 B/s、写 4,000,000 B/s，Nice=15、idle I/O、UMask=0077；块设备先使用 findmnt/systemctl 核实。这些是备份独立预算，不改采集和渲染限额。

工具以 mode=ro 打开源库，只允许 WAL 模式，使用 SQLite backup API 和固定读事务获取同一时点的完整数据库。并发写入仍可继续；读事务会暂时保留 WAL，备份默认最多运行 1200 秒，不能无限持有。在线副本可能早于备份完成时的生产最新快照，这是正常的一致性时间点，不应拿动态源库最新值强行判失败。

输出父目录必须私有 0700，备份文件 0600。先生成唯一临时文件，确认快照/当前表/名册聚合元数据一致、关闭独立副本 WAL 依赖、fsync 后用硬链接无覆盖发布；已有输出绝不覆盖。失败时不发布完成文件，正常异常会清理本次临时文件。进程被强制终止可能遗留 `.backup-*`，它不是有效备份；只在确认所属作业已经结束后处理，不扫描或删除其他备份。

## 恢复演练

`python -B -m app.database_backup verify --backup /私有目录/备份.db --restore-dir /已存在父目录/新的演练目录`

演练目录必须全新，不能指向生产目录。工具逐块复制备份到 `restored.db`，计算备份 SHA-256，在副本上运行 SQLite quick_check、核对应用表和快照/当前榜/名册聚合元数据，并进行创建表、插入和回滚检查。通过后写入私有 `verification.json`。quick_check 不等同于全量 integrity_check，也不代表每个历史业务字段语义都已复核。

备份与恢复是两个独立阶段：备份完成后，即使演练被中断，也可用同一备份和另一个全新演练目录继续验证，无需重新扫描生产数据库。单次备份中断则重做，不尝试将半成品续接为一致性副本。失败演练不会写成功证明，也不会覆盖源库。

## 真正恢复生产时

这属于单独的有状态维护，不是执行 verify。先安排维护窗口、停止数据库写者、保存故障现场；确认备份校验和、成功证明与实际数据时间，避免遗留 WAL 与替换后的 DB 混用。替换、权限、回滚保留与重启需要独立执行方案；本工具故意不提供覆盖生产数据库的恢复命令。

恢复后的历史快照号可能落后于 share，不能直接启动后让新数据库重复使用已有不可变历史 ID。必须一起规划 DB/share 一致性和数据缺口处置，禁止随意删除历史 gzip 或改写历史索引来绕过冲突。恢复演练完成不代表上述灾难恢复流程已在生产执行。

## 定时备份与留存

systemd/oj-rank-backup.service 与 .timer 为独立可选模板。替换 __PROJECT_ROOT__ 和经核实的 __IO_DEVICE__，验证 unit 后安装并启用 timer；六服务安装脚本不包含备份。默认每日 Asia/Shanghai 03:40 加最多 10 分钟随机延迟，错过不立即补跑。失败每小时重试，六小时最多启动三次。

调度器开始前检查资源压力，受独立 CPU/内存/I/O 限额约束；自动备份位于 backups/auto/YYYY-MM-DD，恢复校验成功后保留最近三份受管理备份。手工及未完成备份不会自动删除。首次触发后核对 verified.json，启用 timer 不等于备份成功。同盘备份不能应对整机丢失，异机存储另行配置。
